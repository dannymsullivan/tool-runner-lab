            When would I write the loop myself?
            
    Use Tool Runner when you want the usual request → tool → result → next request cycle handled for you. It also exposes controls for inspecting results and changing the conversation. Write a manual loop when your application's needs do not fit those controls—for example, a particular approval or dispatch workflow.
    
            
    Both approaches still need your business rules, reliable tools, and checks that actions actually happened.       UNDER THE HOOD
      The runner handles the loop.
      Your tools do the work.
      Claude decides what to call and with which inputs. The application executes that code and returns the result. A final message is useful; an independent check tells you what actually happened.
      01 / DECIDE
      The model chooses
      Tool descriptions and input schemas tell Claude what is possible. Its response can request a tool instead of answering the customer.
      02 / EXECUTE
      Your code acts
      An order lookup reads the database. A return tool writes a record. Validate inputs and enforce policy here, where the operation happens.
      03 / VERIFY
      Check the evidence
      Compare the final answer to the actual ledger. Tests catch failed writes and broken policy that a plausible answer can conceal.
      A manual loop
      Illustrative Python snippet
      while True:
    response = client.messages.create(
        model=model,
        messages=messages,
        tools=tool_schemas,
        max_tokens=1024,
    )
    messages.append({
        "role": "assistant",
        "content": response.content,
    })
    if response.stop_reason != "tool_use":
        break
    results = execute_tool_calls(response)
    messages.append({
        "role": "user",
        "content": results,
    })
      Your loop collects tool results and sends them back. execute_tool_calls is application code that returns API-format tool result blocks.
      With the tool runner
      Illustrative Python snippet
      from anthropic import beta_tool

@beta_tool
def lookup_order(order_id: str) -> str:
    """Look up an order by its ID."""
    return read_order_as_json(order_id)

runner = client.beta.messages.tool_runner(
    model=model,
    max_tokens=1024,
    messages=messages,
    tools=[lookup_order],
)

for message in runner:
    inspect(message)
      The SDK replaces the repeated glue code: tool dispatch, result formatting, conversation updates, and the next API call. read_order_as_json and inspect are application helpers. Your tool code still owns correctness.
      What really runs?
      Scripted model responses
      Repeatable messages stand in for model replies. No model API call or API key is needed. You can compare the same case under different conditions.

      The Anthropic SDK Tool Runner executes actual Python functions against SQLite. Faults and verification are real; the lab does not animate a pretend outcome.
